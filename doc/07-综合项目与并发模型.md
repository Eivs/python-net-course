## 新增的两个 HTTP 特性

### ① Range 请求（断点续传 / 视频拖动进度条）

```
请求:  Range: bytes=0-99            响应: 206 Partial Content
                                       Content-Range: bytes 0-99/<总长>
请求:  Range: bytes=-50             响应: 206，最后 50 字节
请求:  Range: bytes=<超过文件大小>-  响应: 416 Range Not Satisfiable
```

实现的核心是 `parse_range()`：它要处理 `start-end`、`start-`、`-suffix` 三种写法，
并且**对越界做校验**（否则就是另一个「长度没上限」的漏洞）。

### ② 缓存协商（省流量的关键）

```
首次:   响应带 ETag: W/"<mtime>-<size>" + Last-Modified
再次:   请求带 If-None-Match: <那个 ETag>
        没变 -> 304 Not Modified（无 body）
```

**为什么用 mtime+size 而不是内容哈希**：便宜。内容哈希更准但每次都要读整个文件，
静态文件服务器通常不值得（这条权衡本身就是工程判断的例子）。

## 两种并发模型

### 模型 A：每连接一线程（`ThreadedServer`）

```python
while True:
    conn, _ = listen_sock.accept()
    threading.Thread(target=handle, args=(conn,), daemon=True).start()

def handle(conn):
    buf = bytearray()
    while True:
        request, consumed = parse_request(buf)     # 阻塞式读
        ...
```

- 优点：写法直观、任何阻塞调用（数据库、磁盘）都不会拖累其他连接；
- 缺点：连接数 = 线程数。1 万条空闲长连接就是 1 万个线程（每个线程栈默认几百 KB ~ 几 MB）。

### 模型 B：单线程事件循环（`SelectorServer`）

```python
selector.register(listen_sock, EVENT_READ, data=None)
while True:
    for key, mask in selector.select(timeout=0.3):
        if key.data is None:
            accept()                                  # 新连接
        else:
            serve(key.fileobj, key.data, mask)        # 已有连接: 先读后写
```

每个连接的状态：

```python
class _Conn:
    __slots__ = ("sock", "inbuf", "outbuf", "close_when_drained")
```

| 事件 | 处理 |
|---|---|
| 可读 | `recv` → 进 `inbuf` → 能解析出完整请求就生成响应 → 追加到 `outbuf` |
| 可写 | `send(outbuf)`，只发得出去多少发多少（**部分写**），剩下等下次可写事件 |
| 读报错/EOF | `drop(sock)`（注销 + 关闭） |

- 优点：连接数与线程数解耦，1 万条空闲连接只是 1 万个 socket 结构；
- 缺点：**任何一次阻塞调用都会拖住所有连接**；代码复杂度明显上升（状态机 + 缓冲区 + 部分写）。

这套思路就是 Java NIO / Node.js / nginx / Redis 的同一条路线。

## 【实测】两种模型压测对比

```text
  模型 / 客户端行为                                  请求数    耗时(s)      QPS  P50(ms)  P99(ms)    错误
  ThreadedServer / 长连接                        320     0.07   4607.2     1.32     2.45     0
  ThreadedServer / 短连接                        160     0.05   3057.5     1.39     2.99     0
  ThreadedServer / 长连接（TLS）                   160     0.04   3974.6     1.36     2.72     0
  SelectorServer / 长连接                        320     0.03   9589.8     0.08     0.12     0
  SelectorServer / 短连接                        160     0.03   6232.4     0.09     0.20     0
```

（8 个并发客户端，下载 64KB 的 `/app.js`，本地回环。）

**怎么读这张表：**

1. **长连接 vs 短连接**：线程模型 4607 → 3057 QPS（掉 34%），事件循环 9589 → 6232（掉 35%）。
   短连接每次都要付三次握手 + TIME_WAIT（第 10、13 课）。**这是"用连接池"最硬的证据。**
2. **线程 vs 事件循环**：本地回环上事件循环快一倍（9589 vs 4607），P99 差 20 倍（0.12ms vs 2.45ms）。
   原因：Python 有 GIL，线程切换 + 锁竞争纯属额外开销；而回环 IO 快得不需要线程去"等"。
3. **TLS 的代价**：线程模型加 TLS 后 3974 QPS（比同条件长连接 4607 低约 14%）。
   真实网络上 TLS 还要多一个 RTT（TLS 1.3）和加解密开销，但会有会话复用抵回来。
4. **两个模型的差距在高并发下才会拉开**：连接数从 8 涨到 8000 时，
   线程模型会先耗尽内存/线程，而事件循环只是多几个 socket 结构。

**注意这张表的局限（诚实声明）**：本地回环没有真实网络延迟，
所以它测的是「协议处理 + 系统调用开销」，不是真实吞吐上限。
真实评估请用 `wrk` / `hey` / `vegeta` 在真实网络上压，并看 P99 和错误率，而不是平均值。

## 【清单】这个项目离生产还差什么

```
□ 请求体大小限制、慢速攻击（slowloris）防护
□ 超时分层可配（连接/读/空闲 keep-alive），现在固定 5 秒

□ 更多安全头（CSP、X-Content-Type-Options）、符号链接处理
□ 压测用专业工具 + 真实网络
```

## 【坑】

- **事件循环里调了阻塞函数**：整个服务卡住（这是异步编程最经典的 bug）——
  正确做法是把慢操作丢进线程池（`asyncio.run_in_executor` 就是这个套路）。
- **非阻塞 `send` 不处理"部分写"**：`outbuf` 没发完就丢弃 → 客户端收到半个响应。
- **`selectors` 里忘记 `modify` 事件类型**：一直在等可写事件但缓冲区是空的 → 空转烧 CPU。
- **压测在回环上做**：结论不能直接搬到真实网络（尤其是吞吐和延迟）。
- **只看平均值**：P50 好看但 P99 是 1 秒的服务，用户依然会投诉。
