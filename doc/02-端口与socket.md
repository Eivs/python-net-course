# 第 2 章：端口与 socket（第 5~7 课）

本章解决的问题：**「数据要交给机器上的哪个进程」**。
三课分别是：端口是什么 → 怎么查谁占了端口 → 怎么判断端口开没开。

代码：`02_port_socket/demo_05_port_basics.py` ~ `demo_07_port_scan.py`

---

## 第 5 课：端口，怎么找到机器里的那个进程

**一句话**：端口是 16 位整数；内核用**五元组**区分连接，所以一个监听端口能同时服务海量客户端。

### 【原理】五元组 + 端口的分段

```
五元组 = 协议(TCP/UDP) + 源IP + 源端口 + 目的IP + 目的端口
        只要有一个不同, 就是两条完全独立的连接
```

| 区间 | 名称 | 说明 |
|---|---|---|
| 0 | 特殊值 | bind 时表示「随便给我一个空闲端口」 |
| 1~1023 | 系统端口 | Unix 上要 root 才能 bind（80/443/22…） |
| 1024~49151 | 注册端口 | 普通服务用（3306/6379/8080…） |
| 49152~65535 | 临时端口 | 内核给客户端随机分配源端口用（本机实测） |

### 【代码要点】

```python
# 端口只有 16 位：超过 65535 直接打包失败
struct.pack("!H", 65536)      # struct.error: 'H' format requires 0 <= number <= 65535

# bind 的地址决定「谁能连进来」
s.bind(("0.0.0.0", 8080))     # 所有网卡都接受连接（对外服务）
s.bind(("127.0.0.1", 8080))   # 只有本机能连（本地开发最安全）
s.bind(("", 0))               # 端口 0 = 让内核分配
```

### 【实测】`02_port_socket/demo_05_port_basics.py`

```text
    端口 65536 -> 打包失败: 'H' format requires 0 <= number <= 65535
    这就证明了端口只有 16 位: 最大 65535。端口号是「稀缺资源」的根源。
    socket.htons(0x1F90=8080) = 0x901F
  getservbyname('http', 'tcp') = 80
  getservbyname('https', 'tcp') = 443
```

**bind 地址决定了谁能连进来**（同一个端口，换目标 IP 就连不上）：

```text
  实测: bind(('127.0.0.1', 0)) 之后 getsockname() = ('127.0.0.1', 60817)
        -> 内核分配的端口是 60817，监听地址是 127.0.0.1
  从 127.0.0.1 连 60817: 连接成功 -> ('127.0.0.1', 60818)
  从 192.168.1.10 连 60817: 被拒绝(ConnectionRefusedError: [Errno 61] Connection refused)
        <- 同一个端口, 只因为目标 IP 不在监听范围内, 连不上。
```

**端口 0 与临时端口范围**：

```text
  连续两次 bind 端口 0 -> 内核给了 60820 和 60821（一般都在临时端口区间）
    net.inet.ip.portrange.first = 49152
    net.inet.ip.portrange.last  = 65535
```

**端口冲突与 `SO_REUSEPORT`**：

```text
  第二次 bind 同一个端口 60819: 失败 -> OSError: [Errno 48] Address already in use
        errno.EADDRINUSE: 端口已被占用。这就是「端口冲突」的真面目。
  双方都设置 SO_REUSEPORT 后再 bind 60819: 成功
```

注意两者的区别（面试常问）：

| 选项 | 作用 | 存在意义 |
|---|---|---|
| `SO_REUSEADDR` | 允许 bind 处于 TIME_WAIT 的地址 | **重启服务器**必备（第 13 课实证） |
| `SO_REUSEPORT` | 允许「同时」多个 socket 监听同一端口并分摊连接 | 多进程负载均衡（gunicorn/nginx 多 worker） |

**五元组的真身**（两个客户端连同一个服务端口）：

```text
  服务端正在 127.0.0.1:60823 上监听
  [服务端 accept] 新连接来自 ('127.0.0.1', 60824)，服务端本地端 ('127.0.0.1', 60823)
  [客户端 1] 本地端 ('127.0.0.1', 60824) -> 对端 ('127.0.0.1', 60823)
  [服务端 accept] 新连接来自 ('127.0.0.1', 60825)，服务端本地端 ('127.0.0.1', 60823)
  [客户端 2] 本地端 ('127.0.0.1', 60825) -> 对端 ('127.0.0.1', 60823)
```

`netstat -an -f inet -p tcp` 里就是同一件事（4 行：2 条连接 × 两端各 1 行）：

```text
    tcp4       0      0  127.0.0.1.60823        127.0.0.1.60825        ESTABLISHED
    tcp4       0      0  127.0.0.1.60825        127.0.0.1.60823        ESTABLISHED
    tcp4       0      0  127.0.0.1.60823        127.0.0.1.60824        ESTABLISHED
    tcp4       0      0  127.0.0.1.60824        127.0.0.1.60823        ESTABLISHED
```

读 netstat 的列：`Proto Recv-Q Send-Q Local Foreign (state)`。
**`Recv-Q`/`Send-Q` 长期非 0 说明有数据堆在缓冲区没人读**，是最典型的性能问题信号。

### 【坑】

- 测试代码写死端口号 → 端口被占就挂。用 `bind((host, 0))` + `getsockname()` 拿真实端口。
- `bind(("", port))` 和 `bind(("0.0.0.0", port))` 等价，都是通配；别以为是「本机」。
- 端口不是「进程独占」：一个进程可以有几百个 socket；反过来一条监听 socket 可以服务上万个连接。

### 【练习】

把第 5 课里的 `bind(("127.0.0.1", 0))` 改成 `bind(("0.0.0.0", 0))`，
再从内网 IP 连同一个端口，观察「被拒绝」变成「连接成功」。

## 第 6 课：谁占了我的端口（实战排障）

**一句话**：`Address already in use` 不是答案，你需要知道**哪个进程、占的哪个地址**。

### 【原理】排障三步曲

```
1) lsof -nP -iTCP:{port}          # 谁在用（-n 不解析域名，-P 不解析端口名，避免拖慢）
2) 如果状态是 TIME_WAIT 而不是 LISTEN -> 代码里加 SO_REUSEADDR
3) 如果是别的进程 -> 换端口，或者去问那个人
```

`netstat -an` 的状态字段还能告诉你更细的信息：

| 状态 | 意味着 |
|---|---|
| `LISTEN` | 正常，等服务连接 |
| `ESTABLISHED` | 连接已建立，可收发 |
| `TIME_WAIT` | 主动关闭方在等 2×MSL；**少量正常**，成千上万说明短连接太多 |
| `CLOSE_WAIT` | 对方关了、**我的代码没 close()** —— 这是 bug，不修永不消失 |
| `SYN_SENT` 大量 | 对端没响应（服务挂了/被丢包/路由不通） |

### 【实测】`02_port_socket/demo_06_port_observer.py`

**系统里都有谁在监听**：

```text
  COMMAND   PID  USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
  nginx    1234  web     9u  IPv4 0x...              0t0  TCP *:8080 (LISTEN)
  postgres 5678  db     11u  IPv4 0x...              0t0  TCP 127.0.0.1:5432 (LISTEN)
  sshd      901  root    3u  IPv6 0x...              0t0  TCP *:22 (LISTEN)
```

（本段已脱敏：进程名 / PID / 用户名换成了通用示例。）

`*:8080` 表示绑定在 `0.0.0.0:8080`（所有网卡），而 `127.0.0.1:5432` 表示只有本机能访问。
**这个区别决定了服务能不能被外部访问，也是安全审计的第一眼。**

**自己起的服务能被 lsof 认出来**（含启动命令）：

```text
  lsof 里查这个端口:
    python3.1 <PID> <用户名>    3u  IPv4 0x...      0t0  TCP 127.0.0.1:<端口> (LISTEN)
  解读: 进程名=python3.1 PID=<PID> 用户=<用户名> 监听地址=127.0.0.1:<端口>
  把这个 PID 拿去 `ps -p <PID> -o command=` 就能看到完整的启动命令行,
  这是「线上服务找不到是谁启的」的标准排查套路。
      PID USER COMMAND
    <PID> <用户名> /path/to/python3 ./02_port_socket/demo_06_port_observer.py
```

（本段已脱敏：PID / 用户名 / 家目录换成了占位符。）

**连接状态分布**（示例输出的形状，具体数量随机器与时刻而变）：

```text
  这台机器当前共 <N> 条 TCP socket, 状态分布:
    ESTABLISHED      <多数>
    LISTEN           <几十条>
    TIME_WAIT        <十几条>
    CLOSE_WAIT       <可能有>
```

（本段已泛化：数量随机器而变，所以只保留形状。）

**这里有一个真实的教学点**：跑的时候确实观察到过 `CLOSE_WAIT` —— 说明
有进程收到 FIN 后没关连接。这是真实世界里很常见的连接泄漏（尤其是常驻的 GUI/后台进程），
不是教学编造的例子。排查顺序永远是：`netstat` 看到异常 → `lsof` 定位到 PID → `ps` 看是谁 → 修代码或重启。

### 【坑】

- `lsof` 输出可能包含非 UTF-8 字节（进程名/事件字节），Python 里读要 `errors="replace"`，
  否则会 `UnicodeDecodeError`（本课代码踩过这个坑）。
- `lsof -i` 等价于同时查 TCP+UDP 的 4/6 两类；要精确查用 `-iTCP:port`。
- `netstat` 的地址用「点」分隔端口（`127.0.0.1.60823`），`lsof` 用冒号（`127.0.0.1:60823`）。
  写解析脚本时这是最常见的低级 bug。

### 【练习】

跑起来后另开终端执行 `lsof -nP -iTCP:<打印出来的端口>`，确认内核和工具说的是同一件事。

## 第 7 课：端口扫描的原理（只扫自己的机器）

**一句话**：判断端口开没开，就是发 SYN 看回应：`SYN+ACK`=开，`RST`=关，什么都不回=被过滤。

### 【原理】三种结果

```
客户端发 SYN  ──►  对方回 SYN+ACK   -> 端口开放（三次握手能完成）
              ──►  对方回 RST       -> 端口关闭（主机在，没人监听）
              ──►  什么都不回        -> filtered（防火墙 DROP，无法判断）
```

还有更隐蔽的方式（本课不实现）：SYN 半开扫描（收到 SYN+ACK 立刻 RST，需要 root 造包）、
UDP 扫描（只能靠 ICMP port unreachable 判断，慢且不可靠）。

### 【实测】`02_port_socket/demo_07_port_scan.py`

**第一步：验证三种探测结果**——起一个真实服务，保证有一个「确定开放」的端口：

```text
  本地已启动一个测试服务: 127.0.0.1:62666
  端口 62666 -> open       有进程在监听 -> 期待 open
  端口 1     -> closed     1 号端口基本不可能有人监听 -> 期待 closed (RST)
  端口 65001 -> closed     高端口, 通常没人监听 -> 期待 closed (RST)
```

**第二步：范围扫描 1-1024**：

```text
  扫完 1024 个端口, 耗时 0.05 秒（并发度 128, 单端口超时 0.4s）
  结果统计: open=0  closed=1024  其他=无
  开放端口: []
```

**这里是本课最有价值的一课**：范围扫描一个都没扫到，不是 bug ——
macOS 的系统服务**都用高位端口**，而真实扫描器也从不真的扫 1-65535。

**第三步：改成「常见端口字典」再扫**：

```text
  扫了 18 个常见端口, 耗时 0.00 秒
  开放的端口（含我们刚起的 62666）: [5000, 7000, 62666]
```

`5000`/`7000` 是 macOS 的系统服务（对应第 6 课 lsof 里那个 `ControlCe` 进程），
`62666` 是我们自己起的测试服务。**字典扫描才是实战姿势**。

**第四步：服务识别（banner）**：

```text
  端口 5000   banner: (读取失败: TimeoutError)
  端口 7000   banner: (读取失败: TimeoutError)
  端口 62666  banner: (无 banner, 静默服务)
```

banner 就是服务主动吐出来的第一行。注意 5000/7000 的「TimeoutError」也是信息：
它们是 HTTP 类服务，你不发请求它就不说话 —— 这也算一种指纹。

### 【坑】

- **不设超时的扫描器遇到 DROP 会永远卡住**；一定要设超时并区分「关闭」和「被过滤」。
- **不限并发的扫描器会耗尽自己的 fd**（macOS 默认 `ulimit -n` 可能只有 256）。
- 「端口能连上」不等于「服务健康」：进程在但业务卡死时，TCP 连接照样成功。
  健康检查要用应用层（`GET /healthz`），别用 TCP connect。
- 法律与道德：**只扫你自己拥有的资产**。扫别人在多数辖区违法，且必触发告警。

### 【练习】

改 `TARGET` 扫你自己家路由器的内网 IP（你有授权的设备），对比本机扫描的差异
（很可能会看到 `filtered`：家用路由器多数不做端口扫描的回应）。

## 本章小结

| 结论 | 验证方式 |
|---|---|
| 端口 16 位，0 让内核分配 | `struct.pack("!H", 65536)` 直接报错；`bind(.., 0)` + `getsockname()` |
| bind 地址决定「谁能连进来」 | 绑 `127.0.0.1` 后用内网 IP 连接 → `ConnectionRefusedError` |
| 内核靠五元组区分连接 | 两个客户端连同一端口，源端口不同；netstat 里看到 4 行（两端各 1 行/连接） |
| `SO_REUSEADDR` ≠ `SO_REUSEPORT` | 前者解决 TIME_WAIT 重启，后者用于多进程分摊（第 13 课实证） |
| 端口冲突可以精确定位 | `lsof -nP -iTCP:<port>` → PID → `ps` 看到完整命令行 |
| 状态字段能区分「正常关闭」和「代码没关」 | 本机实测到 10 条 CLOSE_WAIT（真实连接泄漏） |
| 扫描要区分 open/closed/filtered | 三种结果各自实测一次 |
| 字典扫描 > 范围扫描 | 1-1024 扫出 0 个，18 个常见端口扫出 3 个 |
